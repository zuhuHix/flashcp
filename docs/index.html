flashcp

Copy thousands of small files to and from USB drives as normal loose files. Measured up to 10.3× faster writes and up to 26.8× faster reads than mount + cp on a USB SSD under Linux, and up to 5.7× on a cheap USB 2.0 stick. On a Kingston DataTraveler 3.0 USB 3 stick, writing 20k small files to a blank stick was 34× faster than mkfs + cp (9.02 s vs 304 s, baseline single run). Results vary by drive. See the benchmarks.

Build a fresh volume from a folder (erases the device)

flashcp build ./photos /dev/sdX --yes-erase

Add a folder to a drive that already has files

flashcp add ./photos /dev/sdX1

Pull files off a drive

flashcp pull /dev/sdX1 ./photos-back

Repeat a copy: write only what changed (crash-safe journal)

flashcp sync ./photos /dev/sdX1 --to photos

Make a stick that was filled file by file fast (files kept)

flashcp optimize /dev/sdX1 --yes

Drive mode (desktop package): check it, or turn it off

flashcp drive-mode status
flashcp drive-mode off

Safety: flashcp build erases the whole target device. Check the device path twice before you press enter.

Drive mode

New in 0.3.0, Linux only. Once the desktop package is installed, every USB exFAT drive is served by flashcp's own exFAT driver (flashcp mount, in userspace over FUSE), so copies from any app go through flashcp.

  • What you see. The drive appears as usual at /media/<user>/<LABEL>. Eject shows “Saving…” and then “can be removed”. Pulling it out mid-save gives a warning, and the next plug-in repairs it from the journal. Drives that aren't clean exFAT, or that are busy, fall back to the normal kernel driver.
  • Turning it off. The Speed up USB drives switch in the app or the tray, flashcp drive-mode off, or for every user sudo flashcp drive-mode off --system.
  • Safety. Every metadata write goes through a crash-safe journal on the drive, so after a crash the drive holds the old tree or the new one. The plug-in check runs sandboxed in a transient systemd unit with no network and no access to your files.

Smart copy barely helps (1.08–1.17× on 20k files) because the kernel already batches small writes. The remaining cost is per-file work in the driver, which reordering in userspace does not remove. Pack is fast (4.31–4.93× on 20k files), but it writes a tar archive, not loose files.

Two kinds of drives

Cheap USB 2.0 stick: about 2–5×

The stick measured 6.5 MB/s for sequential 8 MB writes (2.5 MB/s at 4 KB) and about 11 MB/s for sequential reads; a model fit puts its write ceiling at an estimated ≈6.9 MB/s. The chip is the limit, so there flashcp gains about 2–5× (build 3.3–5.3×, add 2.5×, or 5.7× after optimize). Pulling from a stick another system filled is on par with cp until you run optimize once. Big files don't get slower: a 512 MB file copied onto an optimized stick in 86.0 s, against 107.7 s onto a mkfs-default one.

Fast USB SSD: up to 26.8×

The chip is not the limit. On fast drives the per-file overhead is most of the time of a normal copy, so one sequential pass gains up to 10.3× on writes and 26.8× on reads with many small files (2.0–3.2× on the mixed 1.4 GB dataset, where bandwidth is the limit again).

  • Normal copy: at least 3 separate small writes per file (2 metadata writes for the directory entry and allocation bitmap/FAT, plus file data). Large files add one data write per 1 MB, as a rough page-cache flush unit.
  • flashcp: ceil(total bytes / 8 MB) large sequential writes, plus 4 for the boot region and tables.
  • Not modelled: kernel merging of small writes (which real copies do get, see Earlier experiments), queue depth, device firmware. This is a count, not a time prediction.

On the test SSD, 8 MB sequential writes ran at 999 MB/s versus 97 MB/s for 4 KB writes, so turning many small scattered writes into one long ascending run is where the time goes. Each USB command also costs a round trip, so a few 8 MB requests spend far less time on overhead than thousands of small ones.

The journey

Each step was measured before the next one was built. Here is what each one bought, and what it cost.

  1. 1

    Probe the drive

    999 MB/s for 8 MB sequential writes, 97 MB/s for 4 KB writes, about 9k small files/s. The work is about the number of writes, not the number of bytes.

  2. 2

    Smart copy

    1.08–1.17× on 20k files (1.08× smart, 1.17× smart-w4). The kernel already batches writes, and the cost left is per-file work in the driver. Reordering in userspace barely moves it.

  3. 3

    Pack

    4.31–4.93× on 20k files (tar, with adaptive zstd for pack-auto). Fast, but the result is one archive, not the loose files you asked for.

  4. 4

    Build the volume

    Plan the whole exFAT volume in memory and write it as one ascending stream. 6.7× / 10.3× / 2.2× against mkfs + cp on the three datasets. Each build passed fsck.exfat and a byte-for-byte diff, and the result is a normal drive with normal loose files.

  5. 5

    Add and pull

    add writes new files into a volume that already holds files, without erasing it: 3.6× / 5.1× / 2.0× on the SSD. pull reads files off the drive in physical order: 3.0–11.9× on a kernel-filled SSD, up to 26.8× on one that flashcp built.

  6. 6

    The cheap-stick surprise

    The first pull on the stick was 1.8× slower than cp (62.9 s vs 35.2 s). It used the SSD tuning: 32 parallel reads, and reading through 32 KB gaps meant 650 MB read instead of 208 MB. Adaptive reads fixed it: two reads in flight on the stick, and a gap chosen by a ~0.5 s micro-probe. Pulling a flashcp-built stick is now 2.0× (32.78 s to 16.38 s).

  7. 7

    What the speed council concluded

    A 10-agent speed council worked through the stick, and each fix was measured: pull reads now merge adjacent files and match the stick's maximum request size (1 KB layout 39.5 s to 15.9 s, 4 KB layout 22.1 s to 16.6 s), optimize reads the stick only once (81–103 s), and the first copy onto an empty stick runs as a build (104.3 s to 34.9 s). Its conclusion: the next big win is not the drive's physics. It is not re-sending data you already copied. That became flashcp sync: on a 1 GB image with 20k small files, a repeat sync with nothing changed writes 0 bytes, and with 1 % of the files changed 2.4 MB (1.1 % of a full build). It has not been timed on a real stick yet.

Desktop app

A Linux tray app for copying to and from USB drives without a terminal.

  • Drive mode. A USB drives section shows each drive's mode, what is still being saved and Safe to remove, next to the Speed up USB drives switch (also in the tray). See Drive mode.
  • Linux tray app, as a .deb. It starts at login. It has two modes, Copy to USB and Copy from USB, and the app unmounts and remounts the drive for you.
  • File manager entries. Right-click in Nemo, Nautilus or Dolphin for Fast copy to USB (flashcp) or Fast copy from USB (flashcp). Normal file-manager copies are not intercepted.
  • Optimize this stick. The app shows the plan (time estimate, space needed on this computer, what is kept), copies the stick to ~/.cache/flashcp/optimize, verifies it, rebuilds the stick, verifies again and deletes the copy. An interrupted run offers Resume optimize.
  • Trusted drives only. You trust a drive once with an admin password. After that, a small pkexec helper only touches trusted, unmounted USB drives, and runs flashcp as the user.

Windows and macOS: flashcp volumes are checked in CI with Windows chkdsk and macOS fsck_exfat on disk images, not yet on physical USB drives. The desktop app is Linux only.

Honest limits

  • Linux only for now. Windows and macOS can read and write the drives. That is verified on disk images, not yet on physical USB drives.
  • exFAT only.
  • Build erases the target. It writes a whole new volume over the device. Nothing on it survives.
  • Add refuses what it does not fully understand. Volumes that are TexFAT, dirty, or mounted are refused.
  • Cheap sticks are chip-bound. Expect about 2–5× there, not the up to 26.8× of a fast SSD.
  • Optimize needs local disk space for a full copy of the stick (never tmpfs or other volatile storage). If an optimize is interrupted, Windows may offer to format the stick: decline, and run the same optimize again on Linux.
  • Sync trusts size and modification time unless you pass --checksum. Its speed is measured on image files only so far.
  • Simulator accuracy varies by drive. flashcp sim held-out error by workload family: SanDisk 7.1 %, MSI 14.9 %, Kingston 53.5 % (the model lacks a sustained write rate). Real drives remain the judge; see SIMULATION.md.
  • Drive mode needs the desktop package. cp returns about 2× later than with the kernel driver. No symlinks, hard links, xattrs or ownership. Data still being saved when a drive is yanked is lost, as with the kernel's page cache.
  • Unmount first. The device must be unmounted for build and add. The desktop app handles that.

Roadmap

In no fixed order. No dates are promised.

  • Shipped flashcp optimize (rewrites a stick into the fast layout, files kept: copy, verify, rebuild, verify; resumable), automatic cluster size, a per-device speed profile, the device-aware add gap policy, and the first copy onto an empty stick running as a build.
  • Shipped flashcp sync and pull --update / --delete-extraneous (only what changed, with a crash-safe journal), the desktop app's Optimize button, flashcp --version, and the trace-driven simulator flashcp sim.
  • Shipped Drive mode (0.3.0): flashcp mount, a crash-safe exFAT driver in userspace, plus the always-on integration (udev takeover, flashcp drived, the eject guard, the Speed up USB drives switch, flashcp drive-mode).
  • Planned Write-behind and one-click jobs.
  • Planned Windows and macOS versions. Buy Me a Coffee supporters get them first.
